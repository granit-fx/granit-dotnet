## Explore the module reference

Granit has %%PACKAGE_COUNT%% packages organized into categories: Core, Security, Data, Messaging,
Documents, Workflow, Observability, and more. The
[Reference overview](/dotnet/) shows every module with a short description of its
role, so you can quickly find the right package for your use case.

Each reference page covers:

- What the module does and when to use it
- Installation and module dependency declaration
- Configuration options
- Code examples for common scenarios
- Related modules and integration points

## Architecture decisions

Curious why Granit uses CQRS, isolated DbContexts, or Channel fallbacks? The
[Architecture](/dotnet/architecture/) section documents the design decisions behind the
framework, including the constraints that shaped them (GDPR, ISO 27001, multi-tenancy).

Understanding these decisions will help you work with the framework rather than against
it, especially when you encounter patterns like separate Reader/Writer interfaces or
the isolated DbContext checklist.

## Community and contributing

Granit is open-source under the Apache-2.0 license. Contributions are welcome, whether
that is fixing a bug, improving documentation, or proposing a new module.

Check the [Contributing section](/contributing/) to learn about the development workflow,
coding conventions, and Definition of Done that all contributions must satisfy.

:::tip[Pro tip]
If you are building a reusable module for your organization, use the `granit-module`
template from the [Project Templates](/dotnet/getting-started/project-templates/) page. It scaffolds the
correct project structure, test setup, and README so your module follows the same
standards as the framework itself.
:::
